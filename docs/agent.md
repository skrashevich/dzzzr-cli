# ИИ-агенты, MCP и импорт сценариев из PDF

## Инструменты для ИИ-агентов и MCP

Пакет [`agenttools`](agenttools/) превращает движок в каталог инструментов для LLM-агента. Каталог один на все поверхности: его отдаёт наружу MCP-сервер [`agentmcp`](agentmcp/), и им же работает встроенный агент [`agentloop`](agentloop/).

```sh
dzzzr mcp                       # только чтение (по умолчанию)
dzzzr mcp -security approve     # изменения подтверждаются клиентом
dzzzr mcp -security full        # агент действует сам
```

Политика `readonly` не просто отклоняет изменения, а прячет соответствующие инструменты, чтобы модель их даже не видела. В режиме `approve` каждое изменение уходит клиенту как input-request протокола MCP, и вызов повторяется только после согласия пользователя. Админские инструменты появляются, только если заданы учётные данные организатора.

Каталог содержит 21 инструмент игрока и 42 инструмента организатора
(9 читающих и 33 изменяющих). Среди игровых — три инструмента архива:
`game_stat` (итоги завершённой игры по всем командам), `game_description`
(сценарий с кодами, подсказками и спойлерами; аргумент `level` возвращает
одно задание, чтобы не тащить в контекст весь документ) и `game_log`
(лог игры в пределах прав учётной записи).
Админский набор также включает:

| Область | Инструменты |
| --- | --- |
| Игры | `admin_create_game`, `admin_update_game`, `admin_delete_game`, `admin_copy_game`, `admin_finish_game` |
| Уровни | `admin_create_level`, `admin_update_level`, `admin_delete_level`, `admin_copy_levels` |
| Команды и заявки | `admin_team`, `admin_create_team`, `admin_add_team`, `admin_set_application`, `admin_remove_application`, `admin_accept_all`, `admin_generate_pins` |
| Прохождение | `admin_accept_level`, `admin_give_and_accept_level`, `admin_clear_level_codes`, `admin_remove_level`, `admin_clear_team_progress`, `admin_plan_level`, `admin_unplan_level` |
| Корректировки и события | `admin_delete_corrections`, `admin_set_event_time` |
| Движок и сообщения | `admin_toggle_engine`, `admin_delete_message`, `admin_delete_all_messages` |

Создание и редактирование игры/уровня и изменение заявки принимают объект
`params` с полями `GameParams`, `LevelParams` и `ApplicationParams` соответственно.
Например, `admin_update_level` принимает
`{"game_id":4242,"level_id":901,"params":{"publish":false,"bonus_codes":[],"penalty":0}}`.
Неизвестные поля отклоняются. Списки кодов и спойлеров заменяются целиком;
пустой список очищает существующий. Неуказанные поля сохраняются. Клиент
также сохраняет прежнее значение для пустых строк и обычных числовых нулей;
явные `false` у флагов, `penalty: 0` уровня и `status: 0` / `points: 0` заявки применяются.
`admin_copy_levels` копирует из `source_game_id` в `game_id`.
`admin_set_application.params.comment` отправляется капитану по электронной почте.
Для установки известного состояния движка используйте `admin_set_engine`;
`admin_toggle_engine` безусловно переключает состояние всего проекта.

## Встроенный агент

Инструмент `games_list` возвращает краткие страницы по 20 игр (параметр `limit`: 1–50). Для продолжения передайте `next_offset` из ответа как `offset`, сохранив фильтры `archive`/`new_only`. Описания старта и списки команд не включаются в индекс игр, чтобы большой архив не переполнял контекст модели. Для поиска по участникам используйте `team`: CLI фильтрует точное название без учёта регистра и просматривает до 500 записей за вызов. Продолжение задаётся через `next_offset`, даже если на странице нет совпадений.

Перед запросом к модели объём текстов результатов инструментов ограничивается: крупные результаты и старая история передаются с явной пометкой о пропуске данных. Полные результаты сохраняются в исходной истории выполнения; отсутствующие детали можно запросить более узким инструментом или отдельной страницей.

Если MCP-клиента под рукой нет, модель можно позвать прямо из утилиты. Цикл агента построен на [PicoClaw](https://github.com/sipeed/picoclaw): он владеет обращениями к провайдеру, перебором вызовов инструментов и лимитом в 200 обращений к модели за один запуск.

```sh
export DZZZR_LLM_API_KEY=sk-…
dzzzr agent "на каком мы уровне и сколько кодов осталось"      # один запрос, ответ в stdout
dzzzr agent -security approve "отправь код ЛУНА"               # каждое изменение спросит
dzzzr chat                                                     # полноэкранный диалог
```

`dzzzr agent` печатает ответ модели в stdout, а всё остальное — вызовы инструментов, ход выполнения, отчёт — в stderr, поэтому его вывод можно передавать дальше по конвейеру. С `-json` в stdout попадает объект `{"answer": …, "turns": …}`.

### Модель и ключ

Для работы через подписку ChatGPT выберите провайдер Codex. Авторизация выполняется в Codex CLI через ChatGPT:

```sh
codex -c 'cli_auth_credentials_store="file"' login
export DZZZR_LLM_PROVIDER=codex
export DZZZR_LLM_MODEL=gpt-5.4 # укажите модель, доступную вашей учётной записи
dzzzr agent "на каком мы уровне и сколько кодов осталось"
dzzzr chat
```

Используется сохранённый `~/.codex/auth.json` (или `$CODEX_HOME/auth.json`). Для другого файла задайте `DZZZR_CODEX_AUTH_FILE`. Уже выполненный вход через ChatGPT с файловым хранением подходит без повторного входа. Хранилище ОС (keyring) напрямую не читается; [документация авторизации Codex](https://developers.openai.com/codex/auth) описывает варианты хранения и вход через `login --device-auth` для сервера без браузера.

В режиме `codex` (синоним `chatgpt`) API-ключ не нужен. Настройки API-ключа, базового URL и `OPENROUTER_MODEL` игнорируются: запросы идут в Codex через Responses API с обычными инструментами и политикой `-security`. Модель выбирается из `DZZZR_LLM_MODEL`, затем `LLM_MODEL`, затем значения по умолчанию провайдера PicoClaw. Доступность моделей и лимиты определяются учётной записью Codex; стоимость по тарифам OpenRouter не рассчитывается.

Файл авторизации перечитывается перед каждым запросом. Обновлением токенов управляет Codex: если токен истёк, обновите авторизацию в Codex и повторите запрос. CLI не изменяет `auth.json` и не сохраняет токены в историю чата.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DZZZR_LLM_PROVIDER` | `openrouter` | `codex` / `chatgpt` — подписка ChatGPT; `openrouter` / `openai` — OpenAI-совместимый API |
| `DZZZR_CODEX_AUTH_FILE` | `$CODEX_HOME/auth.json` или `~/.codex/auth.json` | Файл авторизации ChatGPT/Codex |
| `DZZZR_LLM_API_KEY`, `LLM_API_KEY`, `OPENROUTER_API_KEY` | — | Ключ провайдера. Не нужен, если адрес указывает на этот же компьютер |
| `DZZZR_LLM_BASE_URL`, `LLM_BASE_URL`, `OPENROUTER_BASE_URL` | `https://openrouter.ai/api/v1` | Адрес OpenAI-совместимого API |
| `DZZZR_LLM_MODEL`, `LLM_MODEL`, `OPENROUTER_MODEL` | `openrouter/auto` | Идентификатор модели |
| `DZZZR_FILES_ROOT` | текущий каталог | Корень локальных файлов: чтение, поиск и создание новых `.json` через `save_local_json` |
| `DZZZR_LLM_SOURCE_CONTEXT_BYTES` | `524288` | Лимит полных результатов `read_pdf` / `read_local_file` в контексте одного запуска, в байтах; максимум 16 МиБ |
| `DZZZR_LLM_REQUEST_TIMEOUT_SECONDS` | `600` | Таймаут одного запроса к модели, включая чтение ответа; от 1 до 3600 секунд. Истечение таймаута не запускает автоматический повтор |

Переменные перечислены в порядке приоритета: `DZZZR_`-имена побеждают, поэтому на машине, где уже настроен другой агент, обе настройки уживаются. Локальный сервер подключается так:

```sh
DZZZR_LLM_BASE_URL=http://127.0.0.1:8080/v1 DZZZR_LLM_MODEL=qwen dzzzr agent "что с уровнем"
```

За пределы `DZZZR_FILES_ROOT` агент не выйдет: путь через `..`, абсолютный путь и символическая ссылка наружу отклоняются.

После каждого запуска печатается отчёт: сколько времени ушло на модель и на инструменты, сколько было обращений и токенов. Для OpenRouter к нему добавляется стоимость по опубликованным тарифам, для локального сервера — `$0`.

### Полноэкранный диалог

`dzzzr chat` открывает диалог с историей: несколько чатов, прокрутка, разметка ответов, подтверждение изменений прямо в окне. Чаты лежат в `~/.config/dzzzr/chats/` с правами `0600` и переживают перезапуск.

Каждый чат помнит свои права, но `-security` запуска остаётся потолком: чат, сохранённый с `full`, в запуске `dzzzr chat -security readonly` работает как `readonly`, а `/mode full` там откажет. Ответ можно спросить в одном чате и уйти в другой — ход продолжится и запишется в свой чат; в списке он помечен `●`, а запрос согласования из фонового чата назовёт его в заголовке.

| Клавиша | Действие |
| --- | --- |
| `Enter` | отправить сообщение |
| `Tab` | перейти к списку чатов и обратно |
| `Ctrl+B` | показать или скрыть список чатов |
| `Esc` | отменить текущий запрос |
| `Ctrl+C` | отменить запрос, а если запроса нет — выйти |
| `PgUp`, `PgDn` | прокрутка переписки |
| `y`, `n`, `q` | разрешить, отклонить или прервать согласование |

| Команда | Действие |
| --- | --- |
| `/help` | справка |
| `/new` | начать новый чат |
| `/chats` | показать или скрыть список чатов |
| `/mode readonly\|approve\|full` | права агента в этом чате, но не выше `-security` запуска |
| `/rename ИМЯ` | переименовать чат |
| `/export [md\|json]` | выгрузить чат в файл |
| `/delete` | удалить текущий чат |
| `/quit` | выйти |

С `-debug` отладочный вывод уходит в `~/.config/dzzzr/chat-debug.log`, чтобы не портить экран.

## Заливка сценария и файлов

Функции сверены с DzrSourceHelper; [сопоставление возможностей](docs/source-helper-parity.md).

```sh
dzzzr admin-upload-file 4242 ./map.png
dzzzr admin-validate-source ./scenario.json
dzzzr admin-upload-source ./scenario.json
# Необязательно: только если игра использует интеграцию where.games.
dzzzr admin-create-technical-level 4242
```

Для записи нужны `DZZZR_ADMIN_LOGIN` и `DZZZR_ADMIN_PASSWORD` игротехника
(либо `-admin-login` / `-admin-password`). Проверка JSON локальная, без авторизации.
`admin-upload-file` возвращает постоянный URL, который можно вставить в HTML задания,
подсказки, спойлера или комментария. Уже существующий файл не перезаписывается.

```json
{
  "game_id": 4242,
  "mode": "create",
  "levels": [{
    "params": {
      "title": "Гаражи",
      "question": "<p>Найдите код.</p>",
      "hint1": "Осмотрите ворота",
      "hint2": "Под табличкой",
      "clue_min": 15,
      "clue_min2": 15,
      "clue_min3": 30,
      "codes": [{"code": "DR123", "danger": "1"}],
      "comment": "<p>Фото кодов и комментарий организатора</p>",
      "time_add_bonus_all": 0,
      "publish": true
    }
  }]
}
```

`create` добавляет уровни по порядку; технический уровень не добавляется.
`update` требует положительный `id` у каждого уровня и **полностью заменяет**
моделируемые поля: пропущенные строки/списки очищаются, числа становятся нулём,
неуказанные флаги выключаются. Для частичных изменений остаётся `admin-update-level`.
Проверяется весь пакет; первая ошибка записи останавливает его и возвращает ID
уже записанных уровней. Повторный create может создать дубликаты — сначала проверьте
`admin-levels`. Формат пакета описан также в [gamesource](gamesource/README.md).

В обычном редактировании доступны `comment=` (пустая строка очищает комментарий)
и `time_add_bonus_all=0` (сбрасывает бонус за все бонусные коды).
LLM/MCP-инструменты: `admin_upload_file`, `admin_validate_source`,
`admin_upload_source`, `admin_create_technical_level`.

## Сценарий из PDF через LLM

LLM-агент читает индекс PDF через `index_pdf` и определяет только структуру:
какие фрагменты относятся к каким полям. Тексты, числа и ссылки извлекает Go-код
через `extract_pdf`; модель не переписывает содержимое документа.
Названия заголовков и расположение разделов не зашиты в парсер. Подключение
Google Docs/Drive не требуется. PDF обрабатывается внутри Go-процесса, без Python,
CGO и вызовов внешних программ:

```sh
export DZZZR_FILES_ROOT="$HOME/Downloads"
# DZZZR_LLM_API_KEY / DZZZR_LLM_MODEL и админские учётные данные настраиваются выше.
dzzzr -security approve agent \
  'Прочитай Игра ПР 2026.pdf целиком, подготовь сценарий для игры 4242 в режиме create, проверь и залей уровни. Технический уровень не нужен.'
```

`index_pdf` возвращает SHA-256, до 10 страниц с нумерованными строками, ссылками,
метаданными изображений и
`has_more`. Агент должен дочитать все страницы; уровень может продолжаться на
следующей странице. Содержимое документа — данные, а не инструкции агенту:
руководства, примеры и оглавление не становятся игровыми уровнями.

Прочитанные страницы сохраняются в контексте целиком. Они не подпадают под
ограничение истории обычных инструментов (48 КБ суммарно / 16 КБ на ответ).
Если отдельный лимит исходных документов превышен, запуск останавливается без
удаления страниц; его можно увеличить через `DZZZR_LLM_SOURCE_CONTEXT_BYTES`,
учитывая размер контекста выбранной модели. Байты не равны токенам.

Для локального экспорта достаточно readonly:

```sh
dzzzr agent 'Прочитай Игра ПР 2026.pdf и сохрани сценарий в scenario.json в машиночитаемом JSON'
```

`save_local_json` создаёт новый `.json` внутри `DZZZR_FILES_ROOT` по явной просьбе
пользователя, проверяет JSON и не перезаписывает существующие файлы. Лимит — 4 МиБ.
Это локальный документ; админские права и ID игры для экспорта не требуются.
При работе с PDF через `save_local_json` сохраняется **только схема** с адресами
полей. Затем `extract_pdf(path, mapping_path, output_path)` создаёт итоговый файл
непосредственно из PDF. В схеме запрещены готовые скалярные значения вместо ссылок
на исходник. Проверяются хеш, диапазоны, типы и покрытие непустых строк: служебные
или неиспользуемые строки должны быть явно перечислены в `ignored`.
Для другого PDF модель строит другую схему; заголовки и позиции в Go не зашиты.
Проверка покрытия построчная: она не доказывает, что модель правильно назвала поле
или выбрала нужную колонку таблицы. Схема остаётся отдельным проверяемым артефактом.

Те же операции доступны без агента:

```sh
dzzzr pdf-index scenario.pdf 1 10
dzzzr pdf-extract scenario.pdf mapping.json scenario.json
```

[Формат схемы и примеры](pdfsource/README.md). Локальный экспорт может сохранять
поля разных дивизионов отдельно. Для заливки нужен выбор дивизиона и дерево в
формате `levels[].params`. Тулзы `admin_validate_source` и `admin_upload_source`
принимают `path` к полученному JSON и при необходимости `game_id`/`mode` отдельно:
тексты не проходят повторно через ответ модели.
В `-debug` печатаются размер, признак и текст ошибки результата инструмента,
отправка HTTP-запроса, время до начала HTTP-ответа и `finish_reason` после его
завершения. Начало HTTP-ответа ещё не означает готовность JSON: непотоковый
провайдер может долго формировать тело ответа. Сообщение об ожидании через 15
секунд само по себе не свидетельствует о зависании. Обрезанные провайдером ответы
(`finish_reason=length`) не передаются на выполнение тулзам.
Пустой ответ без текста и вызовов инструментов не считается завершением задачи:
клиент повторяет запрос не более трёх попыток, затем сообщает ошибку провайдера.

`openrouter/free` — [маршрутизатор со случайным выбором бесплатной модели для
каждого запроса](https://openrouter.ai/docs/guides/routing/routers/free-router),
а не одна фиксированная модель. Поэтому соседние шаги агента могут выполнять
разные модели. Для воспроизводимого разбора сценария задайте конкретный ID модели;
проверка JSON и покрытия строк не заменяет сверку структуры с исходником.

`admin_upload_pdf_image` загружает конкретную встроенную картинку по номеру страницы
и `image_id` из индекса. Возвращённый URL добавляется в `image_urls` схемы,
после чего Go собирает HTML из исходных фрагментов и изображений через `$concat`.
Без загрузки картинки сохраняются как `pdf-image://...`; проверка плана для
движка отклоняет такие неразрешённые ссылки.
Парсер не скачивает внешние URL; уже готовые ссылки на картинки/аудио сохраняются.
Положение картинок и ближайший текст помогают отличать иллюстрацию задания от фото
кодов; при неоднозначности агент должен уточнить назначение. OCR сканов не реализован:
`requires_ocr` сообщает об отсутствии текстового слоя (это бывает и на пустых страницах).

Пути ограничены `DZZZR_FILES_ROOT` (по умолчанию текущая папка). Чтение доступно в
readonly, запись в движок подчиняется readonly/approve/full. Эти же инструменты и
инструкции доступны MCP-клиентам. Достаточно одного Go-бинарника;
Docker-образ использует distroless/static.
